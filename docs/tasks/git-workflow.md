# 브랜치·커밋·PR 규칙

## 기본 흐름
이슈 → 작업 브랜치 → 구현·검증 → 커밋·PR → 리뷰·수정 → 사용자 병합 결정.

- 이슈 범위로 작업한다. 문서 초기화처럼 아직 이슈가 없으면 없는 번호를 만들지 않고 작업 목적을 기록한다.
- 이 문서는 절차 기준이다. 실제 커밋·푸시·PR 생성은 해당 요청에 포함된 범위에서 진행한다.
- 최종 병합은 사용자가 결정한다. 사용자가 해당 PR 병합을 명시적으로 요청하면 아래 조건을 확인하고 실행할 수 있다. 자동 병합은 설정하지 않는다.

## 브랜치와 커밋
- main을 기준으로 codex/이슈번호-짧은-영문설명 형태를 사용한다. 이슈 없는 초기 문서 작업은 codex/docs-workflow처럼 목적을 넣는다.
- 최초 커밋이 없는 저장소에는 비교 기준이 없다. 첫 기준 커밋·원격 기본 브랜치 설정은 별도 승인된 초기화 작업에서 처리한 뒤 정상 PR 흐름을 시작한다.
- 작업 전 상태를 확인하고 사용자의 기존 변경을 보존한다. 관련 파일만 명시적으로 스테이징하고 staged diff를 확인한다.
- 하나의 의미 있는 변경을 한 커밋으로 묶는다. 관련 없는 정리와 기능 변경을 섞지 않는다.
- 메시지 형식은 type(scope): 한국어 변경 설명이다. type은 feat, fix, docs, refactor, test, chore, ci 중 선택한다.
- 예: feat(gathering): 나무 독점 처리 추가 / docs(workflow): 리뷰 완료 조건 정의.
- 본문에는 필요한 이유·이슈 참조를 적는다. 미완료 이슈에는 Refs를 사용한다.
- 검증 실패·미검증 항목을 숨기지 않는다. 공유된 커밋 재작성·강제 푸시는 사용자 요청 없이 수행하지 않는다.

## PR
- 하나의 실행 이슈 또는 독립적으로 검토 가능한 변경을 묶는다. 양쪽 저장소의 PR을 상호 연결한다.
- [PR 템플릿](../../.github/pull_request_template.md)에 문제와 결과, 범위, 관련 이슈, 실행한 검증, 미검증, 리뷰 상태를 작성한다.
- 리뷰 미완료·필수 검증 미완료는 초안 상태로 유지한다.
- 실제로 완전히 해결하는 실행 이슈만 Closes로 연결한다. 대표 이슈·상대 저장소 선행 이슈는 관련 링크로 둔다.
- 공용 계약이 바뀌면 호환되는 클라이언트·서버 버전과 적용 순서를 명시한다.
- 사용자에게 보여줄 제목·본문은 최종 변경 기준으로 정리한다. 작업 중 대화나 폐기한 접근을 길게 옮기지 않는다.

## 병합 조건
- [리뷰 기준](review.md)에 따른 필수 검토 및 해당 변경의 검증 통과.
- 중대한 미해결 지적 없음, 충돌 없음, 관련 요구사항·문서 갱신.
- 마지막 리뷰 이후 변경이 있으면 영향 범위를 재검토하고 관련 검증을 다시 실행.
- 사용자 병합 결정. 기본 제안은 squash 병합으로 실행 이슈 단위 이력을 남기는 방식이다.
- GitHub 보호 규칙은 이 파일만으로 활성화되지 않는다. 실제 필수 체크·보호 설정 도입은 별도 작업이다.
- 이 규칙은 두 저장소에 같은 내용으로 유지한다.
