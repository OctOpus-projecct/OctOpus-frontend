# 이슈 작성 규칙

## 생성 전
- 사용자가 이슈 생성·관리를 요청한 범위에서 GitHub에 등록한다. 규칙 파일 작성만으로 실제 이슈 등록까지 수행하지 않는다.
- 원격 저장소와 기존 열린·닫힌 이슈를 검색해 중복을 확인한다. 겹치면 기존 이슈 갱신 또는 후속 이슈 연결을 우선한다.
- 기준 요구사항에서 확정·제안·미정을 구분한다. 구현을 막는 미정 사항은 결정 작업으로 분리한다.
- 작업 하나는 독립적으로 완료 여부를 확인할 수 있는 범위로 잡는다. 먼 미래의 기능을 세부 작업으로 미리 분해하지 않는다.

## 저장소와 연결
- 서버 판정·저장·공용 계약·배포는 백엔드, 입력·화면·시각 자산은 프런트엔드에 만든다.
- 양쪽 기능을 묶는 대표 이슈는 백엔드에 만들고 저장소별 실행 이슈를 연결한다.
- 대표 이슈에는 전체 완료 조건과 하위 이슈 링크만 관리한다. 같은 상세 요구사항을 양쪽 이슈에 복사하지 않는다.
- 다른 저장소는 전체 이슈 URL 또는 실제 owner/repository#번호로 식별한다. 존재하지 않는 번호를 만들어 넣지 않는다.
- 실행 이슈 하나가 끝났다고 대표 이슈를 닫지 않는다. 관련 작업과 통합 검증까지 끝나야 한다.

## 제목·본문
- 제목은 한국어로 동작과 대상을 구체적으로 표현한다. 예: “동시 벌목 요청에 나무 점유를 한 명만 허용”.
- 기능·문서·환경 설정은 [작업 템플릿](../../.github/ISSUE_TEMPLATE/task.md), 결함은 [버그 템플릿](../../.github/ISSUE_TEMPLATE/bug.md)을 따른다.
- 목적, 포함·제외 범위, 확인 가능한 완료 조건, 선행·관련 이슈, 기준 문서 경로를 작성한다.
- 버그는 재현 순서, 기대·실제 결과, 환경과 영향 범위를 추가한다. 비밀값과 개인정보가 든 로그는 제외한다.
- 완료 조건은 “테스트 작성”보다 “동시 요청 두 건 중 하나만 점유 성공”처럼 결과로 쓴다.
- 레이블은 feature, bug, docs, setup을 기본 후보로 사용하되 실제 존재 여부를 확인한다. 없으면 임의로 필수 처리하지 말고 미적용 사실을 보고한다.
- 웹 UI 템플릿이 CLI/API 본문에 자동 적용된다고 가정하지 않는다. 등록 도구에서도 같은 본문 구조를 직접 채운다.
- GitHub 이슈·PR 본문에서 파일을 링크할 때는 실제 원격 URL과 ref를 확인한다. 로컬 파일 경로를 웹 링크처럼 넣지 않는다.

## 진행과 종료
- 진행 상태·막힌 이유·남은 일은 해당 이슈에 간결하게 갱신한다. 의미 없는 진행 댓글은 반복하지 않는다.
- 실제 완료 조건을 충족한 실행 이슈만 해결한 PR에서 닫는다. 미구현·미검증 상태는 완료로 처리하지 않는다.
- 도구 응답이 불확실하면 중복 생성 전에 다시 조회한다.
- 이 규칙은 두 저장소에 같은 내용으로 유지하며 변경 시 양쪽을 확인한다.
